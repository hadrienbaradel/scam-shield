# Browser pages: judging the page the senior is looking at
Answers how Scam Shield can judge a scare pop-up or a fake login page in the senior's browser, on which browsers and platforms, what it needs, how long it takes and what fits before Nov 4. Written 2026-10-28 from the browser-channel research note; day figures are the researcher's estimates for a two-person team.

## Decision
For Nov 4: one Manifest V3 extension loaded unpacked in Chrome (the same package loads in Edge) for a 15 s pop-up scene (a fake "Microsoft" page goes full-screen with a phone number; the extension exits full-screen, covers the page with the verdict card in 19 px+ type, reads it aloud, one tap closes the tab or asks the daughter) plus a toolbar "Check this page" button. It is the same extension as the planned Gmail "Check this" (one manifest, three entry points): 2.5-3 days plus 0.5 day of server work, a stretch next to the live-inbox gate, so if time runs short ship only the on-demand `activeTab` button and film that. After Nov 4, for real seniors: submit that extension to the Chrome Web Store (Unlisted first) and Edge Add-ons with the always-on page watcher as an optional runtime permission the relative grants at setup, and add the NextDNS denylist push (1-1.5 days) so a confirmed host is blocked on every device at home, iPhone included. Why: desktop Chrome and Edge are where the scare pop-up happens and where an unpacked install takes seconds; Android Chrome has no extensions; Safari needs a wrapper app, the US$99 program and per-site grants (3-5 days); the native layers miss personal context, phone-number lures, Standard-protection Chrome users and the plain-words next step.

## Build sheet
- **MV3 extension, unpacked (Chrome, Edge)**
  - Sees: `chrome.tabs.captureVisibleTab` (visible area of the active tab; needs `<all_urls>` or `activeTab`; chrome:, data: and other extensions' pages only with `activeTab`; at most 2 calls/s, `MAX_CAPTURE_VISIBLE_TAB_CALLS_PER_SECOND`, Chrome 92+); `url`, `pendingUrl`, `title`, `favIconUrl` through the `tabs` permission or host access to the page; page text and DOM through declared content scripts or `scripting`.
  - Install warning strings (Chrome): `tabs` and `webNavigation` "Read your browsing history."; `declarativeNetRequest` "Block content on any page." (implicit allow, allowAllRequests and block); `declarativeNetRequestFeedback` "Read your browsing history." (no effect on store installs); `notifications` "Display notifications."; `activeTab`, `scripting`, `storage`, `sidePanel`: none; `declarativeNetRequestWithHostAccess`: none, but host permission is needed per host; the `tabs` warning disappears when `<all_urls>` is requested; the all-sites host string is commonly "Read and change all your data on all websites" (unverified). Changing `content_scripts.matches` triggers a warning; `optional_host_permissions` are granted at runtime instead of install.
  - Two profiles, one codebase: (a) "Check this page" = `activeTab` + `scripting`, no warning, screenshot and text only on the tap; (b) watcher = `optional_host_permissions: ["<all_urls>"]` + `webNavigation` + `declarativeNetRequest(WithHostAccess)`, granted at setup by the relative. Ship (a) first for a short review; (b) is what protects a senior who will not tap in panic.
  - Scare signals without the model (content script or service worker, instant): `document.fullscreenElement` set shortly after load; `document.pointerLockElement` set; a burst of `webNavigation.onHistoryStateUpdated` on one tab (history trap); audio or video playing with no gesture; a phone-number regex plus "call", "Microsoft", "Apple", "virus", "blocked" in `document.body.innerText`; keyboard-lock API use is Chrome's own trigger. Any one plus a fresh domain (existing RDAP age check) shows the overlay before Muse answers; Muse then writes the plain-words reason (~4.7 s at low effort, 20 s deadline).
  - Overlay and full-screen: a full-screen element hides the rest of the document, so call `document.exitFullscreen()` first (no user gesture needed), then append the overlay to `<body>`; the fallback `chrome.tabs.update(tabId, {url: chrome.runtime.getURL('warning.html')})` always wins because it leaves the page. Keyboard or pointer lock makes the senior's clicks unreliable but not the service worker. Test on day 1.
  - Actions: "Close this window" = `tabs.remove()` on the senior's tap, never automatic; afterwards a dynamic `declarativeNetRequest` `block` rule for the host (limits: 30,000 safe dynamic rules from Chrome 121, 5,000 unsafe redirect/modifyHeaders, 5,000 session); a redirect to an `extensionPath` needs a web-accessible resource. Site notifications cannot be read; clearing a site's notification grant needs `contentSettings` (unverified).
  - Server (half a day): allow the `chrome-extension://<id>` origin or skip the Origin check for device-token requests in `src/server.js`; reuse the Android companion's device token; `POST /api/check/text` with page text, URL and a `captureVisibleTab` JPEG (`/api/check/image` exists).
  - Demo install: Chrome load unpacked in developer mode; Edge `edge://extensions` > Developer mode > Load unpacked (installed like a store extension); Firefox `about:debugging` > This Firefox > Load Temporary Add-on (gone at restart).
  - Scene plan (15 s): day 0.5, a fake scare page under `tests/fixtures` or a demo folder, served on localhost through the tunnel origin (full-screen on click, siren, "Your computer is infected, call +1 (8xx)...", `pushState` loop; absent from Safe Browsing, so no native interstitial); day 1, manifest (`activeTab`, `scripting`, `storage`, `optional_host_permissions: ["<all_urls>"]`, `webNavigation`), content script with the signal detector, service worker calling the API with the device token, server Origin allowance.
  - Day 2, the overlay (shared `verdictCard` from `public/js/ui.js`, `speechSynthesis` read-aloud, "Close this window", "Ask my daughter" through the trusted-person route), `exitFullscreen` plus the warning-page fallback, the DNR block rule, French strings; day 3 (half), pre-cache the verdict in `llm_cache`, rehearse at 150% zoom with 19 px+ type, record. New code ~400-600 lines; 2.5-3 days plus 0.5 server.
  - On video: show the instant rule-based state ("Stop, do not call this number", 2 s minimum) before the Muse reasons so a 5-10 s verdict never looks slow; storyboard: ad result > siren and red screen > 1 s later the page shrinks and the card covers it > voice reads it > tap "Close this window" > the calm inbox.
  - Recording caveat: Chrome's interstitial or Edge's scareware blocker may fire first on a convincing page; record on Chrome with Standard protection (the default) and the locally served page; test once before the take. Answer to "doesn't Chrome already do this?": Enhanced Protection only, no personal context, no phone-number lure, no plain-words next step, no family loop.
  - Fallback in one line: if the overlay fails under full-screen, navigate the tab to `warning.html`; if the extension is not ready, film the `activeTab` button on a plain fake page.
- **Store listings (after Nov 4)**
  - Chrome Web Store: review "within a few days, but it can take up to a few weeks", longer for broad host permissions, sensitive permissions, new developers and new extensions; contact support after three weeks; a 2026-04-23 Chromium PSA reports longer waits and recommends `activeTab` or optional host permissions; Public, Unlisted (no listing, installable by URL) and Private (listed testers) go through the same review; one-time US$5 registration fee (secondary figure, 2020) tied to a developer email that cannot change.
  - Edge Add-ons (Partner Center): Public or Hidden; certification up to seven business days; no remote code; a written justification per permission. Firefox: release builds need Mozilla signing; self-distributed add-ons are signed after automated validation, up to 24 h, longer if picked for manual review; unsigned runs only in Developer Edition, Nightly and ESR.
- **Android browsers**
  - Chrome: no extensions in stock Chrome; only experimental "desktop Android" builds load a .crx by hand (no toolbar button, big screens); the Gemini Nano page check promised for Android in 2025 is unconfirmed. Edge: extensions since 134.0.3124.57 (March 2025), about 22 curated add-ons in a Beta "Extensions" area, no developer submission path found. Firefox: `web-ext run -t firefox-android` over adb with "Remote debugging via USB" on (any edition, temporary; persistent only on Nightly or Beta); Nightly "Install add-on from file" after five logo taps, signed XPI only; AMO open to Android add-ons since 2023-12-14 (over 400 at launch, secondary); `captureVisibleTab` since Firefox 54 on Android.
  - Product path on Android stays the companion app (link-tap interception, share sheet) plus DNS.
- **Safari (Mac, iPhone, iPad)**
  - Safari 14+ on macOS, iOS 15+, visionOS 1+; the WebExtension runs inside a macOS or iOS app extension; `xcrun safari-web-extension-converter` wraps the Chrome package; `captureVisibleTab` from Safari 14 and iOS 15; `declarativeNetRequest` and `webNavigation` on iOS not checked.
  - Distribution: Apple Developer Program US$99/year; App Store Connect for Mac and iOS; TestFlight up to 100 internal and 10,000 external testers (email or public link), the first external build is reviewed, a build lives 90 days; Mac outside the store needs Developer ID plus notarization; Mac beta without signing: send the unsigned app ("Copy App"), the tester allows unsigned extensions; free account: 10 App IDs, 3 devices, profiles expire after 7 days.
  - Per-site grants: `content_scripts.matches` requests access; Safari shows a badge until the user grants; macOS toolbar button: once, for the day, all websites, or deny; iOS: More menu > extension > permission, and Settings > Safari > Extensions (Ask/Allow/Deny per site); Safari 17+ grants cover all profiles and private browsing. Forum reports (unverified): an all-sites grant on iOS 17.5.1 injected nothing until Safari restarted; prompts repeated across sites.
  - Effort: 1 day to wrap and run on the team's own Mac/iPhone, 1-2 days of API and permission UX, plus the program and a first TestFlight review (hours to about two days, secondary reports): 3-5 days, after Nov 4. iPhone path meanwhile: Fraudulent Website Warning, a DNS profile, the share sheet.
- **Native protections in 2026 (what to film around, what to answer)**
  - Chrome: on-device Gemini Nano since Chrome 137 (announced 2025-05-08), triggered by scam behaviour such as the keyboard lock API, extracts page intent, sends it to Safe Browsing for the verdict and shows an interstitial, only for users opted into Enhanced Protection; Standard (the default) checks obfuscated URL parts against lists and sends content only when a site "does something suspicious"; next targets package-tracking and unpaid-toll scams; Google: "the average malicious site exists for less than 10 minutes". Chrome on Android flags spammy site notifications with an on-device model (Unsubscribe / Show), nothing sent to Google.
  - Edge: scareware blocker, a local computer-vision model for full-screen scams, on by default on most Windows and Mac devices with more than 2 GB of RAM and four cores (2025-10-31); Edge 142 (November 2025) adds a real-time report to SmartScreen without screenshots, off by default; in preview each report protected 50 more users on average, but 30% of targeted users had seen the scam before the first report. SmartScreen: page analysis plus reported phishing lists. Safari: Fraudulent Website Warning, Google Safe Browsing and Apple lists (Tencent in mainland China), information computed from the address, no on-page analysis.
  - They miss: personal context ("you do not bank at Chase", "not the number on your Orange bill"); phone-number lures on ordinary pages (no full-screen, no download); every Standard-protection Chrome user; iPhone and iPad (lists only); fresh domains and fake customer-service numbers in search results; the plain-words next step and the family loop.
- **DNS filtering**
  - NextDNS API (beta, "subject to breaking changes"): base `https://api.nextdns.io/`, header `X-Api-Key`; `POST /profiles`, `GET/PATCH/DELETE /profiles/:profile`; `POST /profiles/:profile/denylist` with `{"id": "badwebsite.com", "active": true}` (array endpoints take GET, PUT, POST; children PATCH and DELETE by first key); an invalid domain returns 200 with an `errors` array; security keys `threatIntelligenceFeeds`, `googleSafeBrowsing`, `cryptojacking`, `dga`, `nrd`, `typosquatting`, `aiThreatDetection`; no rate limit or denylist size stated. Plans: free 300,000 queries/month, then it keeps answering without blocking; Pro €1.99/month or €19.90/year, unlimited queries and devices. Apple: signed `.mobileconfig` (file, link or QR), optional NextDNS root CA so the block page loads without an HTTPS warning; Android: Private DNS hostname `<profile-id>.dns.nextdns.io` (unverified).
  - Integration (~1 day plus 0.5 guide): one profile per family; the relative pastes the family's own API key (account-wide, no scoped keys documented, so never one master key), stored encrypted like the Gmail tokens; on a Scam verdict naming a fake login or shop host, excluding shared hosts and shorteners as in `link-checks.md`, `POST .../denylist`; card line "Blocked on every device at home"; unit test with a fake fetch.
  - Cloudflare: 1.1.1.2 / 1.0.0.2 malware, 1.1.1.3 / 1.0.0.3 malware plus adult; DoH `https://security.cloudflare-dns.com/dns-query` and `https://family.cloudflare-dns.com/dns-query`; blocked names resolve to 0.0.0.0; test with `malware.testcategory.com`; Android 9+ Private DNS hostname; iOS through the 1.1.1.1 app (manual DNS covers the current Wi-Fi only); router: the admin console DNS fields. Quad9: 9.9.9.9 / 149.112.112.112, DoH `https://dns.quad9.net/dns-query`, DoT `tls://dns.quad9.net`, about 20 threat feeds, free, Zürich non-profit. CleanBrowsing Security: 185.228.168.9 / 185.228.169.9, DoH `https://doh.cleanbrowsing.org/doh/security-filter/`, DoT `security-filter-dns.cleanbrowsing.org`, hourly refresh, custom filters paid.
  - Home boxes: Freebox `mafreebox.freebox.fr` > Paramètres de la Freebox > Mode avancé > DHCP > DNS 1 and DNS 2 (keep 212.27.40.240/241 as DNS 4/5) > Appliquer > restart or reconnect (third-party guide, 2024-10-19); Livebox 4/5/7: no LAN DNS setting, per-device DNS or a second router (forum, unverified); Bbox: first DNS entry locked, DHCP option 6 entries count from second place (forum, unverified). Device-level setup is the reliable path in France.
  - Steps for the relative: 1) create a NextDNS profile and enable NRD, typosquatting, Google Safe Browsing and threat feeds; 2) Android: Settings > Network & internet > Private DNS > the hostname; 3) iPhone, iPad, Mac: scan the QR at apple.nextdns.io, install the signed profile, optionally trust the root CA; 4) Freebox: DHCP DNS 1/2; Livebox: skip; 5) paste the API key into Scam Shield's family settings; 6) open a known blocked test domain. DNS misses scare pages on legitimate hosts or CDNs, fake numbers in search ads, fake shops on established domains and anything reached by IP.
  - Fallback in one line: no code at all, the relative sets Cloudflare 1.1.1.3 or Quad9 on the phone and the box (15 minutes, known phishing hosts only).
