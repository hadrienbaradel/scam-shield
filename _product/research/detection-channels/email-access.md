# Email access beyond the Gmail API: IMAP, Microsoft Graph, forward-to-check
What Scam Shield can read and mark in a senior's mailbox when it is not Gmail (French ISPs, La Poste, iCloud, Yahoo/AOL, Outlook.com), what each path needs, how long it takes and what fits before Nov 4. Written 2026-10-28; "(unverified)" marks claims not checked against an official page; "probe" means the pre-login CAPABILITY banner read from each IMAP server on 2026-10-28 (`openssl s_client -connect host:993`), which can omit extensions that appear only after login.

## Decision
Nov 4: build forward-to-check on a polled `check@` Gmail mailbox under the built Gmail sync (0.5 day), promoted to Resend Receiving on `<id>.resend.app` (1-1.5 days) only if a branded address is worth keeping a tunnel up; it is the one path that covers every French ISP and every US provider in the video without a credential or a public URL, and it reuses `parseEml`, the checker and the Resend sender. After Nov 4, for real seniors: Microsoft Graph for Outlook.com (2-3 days, the same OAuth story as Gmail, a red named category visible in every Outlook client) and the IMAP connector for Orange, SFR, Free, Bouygues and La Poste, then iCloud and Yahoo/AOL (3-4 days, mailbox password at rest, 120 s polling where IDLE is absent), because those two cover the mailboxes seniors actually use. Gmail stays on the API; Gmail over IMAP is never built.
Market share, one line (unverified): France 2019, all ages, Gmail 26.9%, Microsoft 25.9%, Orange 17.8%; US over-65s 2017, Yahoo 31%, Gmail 24%, AOL 16%.

## Build sheet
- **Forward-to-check, polled `check@` Gmail (0.5 d)**
  - A Gmail account connected through the built sync (`messages.list`/`history.list`, Pub/Sub pull, no public URL); raw message via `messages.get` format=raw; Gmail's `Authentication-Results` covers only the forwarder's hop. Testing-mode consent expires every 7 days (feasibility #3); no custom address.
  - Parser: an inline forward keeps only quoted text (Gmail's "---------- Forwarded message ---------" block: From/Date/Subject/To), display name, links and their domains, attachments (PDF/image to Muse); treat all of it as untrusted text. The original SPF/DKIM/DMARC, `Received` path and Message-ID are gone. A `.eml` attachment goes to the existing `parseEml` (`src/google/eml.js`) and is judged like a synced message; the repo already trusts original authentication only "if Gmail visibly received it".
  - "Forward as attachment" exists on Gmail web (tick the message > More > Forward as attachment; wrapped as `.eml`; over 25 MB via Drive; documented for computers only), classic Outlook (More Respond Actions > Forward as Attachment), Outlook for Mac 16.58+, Apple Mail macOS (Message menu (unverified)); new Outlook/Outlook.com has only drag-and-drop into a draft and a rules action; Gmail mobile and iPhone Mail have none (unverified); Outlook for Android under the More menu (unverified).
  - Abuse: accept only registered seniors (header From and envelope from), require the forwarder's own SPF/DKIM pass, per-senior `check+<token>@`, rate limit per sender, drop everything else silently (no bounce, no backscatter).
  - Reply: the existing Resend sender from our domain, deep-linking to the verdict page (public HTTPS, feasibility #25); the mail says what it could not check ("forwarded, so the real sender is unverified; forward it as an attachment from a computer for a full check").
  - Steps: 1) the relative registers the senior's address once; 2) the senior taps Forward, types `check@...`, sends; 3) the verdict mail arrives. Fallback: screenshot into the existing image check.
- **Forward-to-check, Resend Receiving (1-1.5 d)**
  - Receive at `<id>.resend.app` (no DNS) or at a verified custom domain with one MX record (any address at the domain). Webhook `email.received` carries `email_id, from, to, cc, bcc, subject, message_id, attachments[] (id, filename, content_type)`, never body or headers: call the Received emails API, then the Attachments API (`download_url` valid 1 hour). Resend stores received mail even without a webhook.
  - Free plan: 3,000 emails/month, 100/day, 3 domains, 1 webhook endpoint, 30-day logs; received mail counts toward the transactional quota; Pro $20/month for 50,000. Needs a public HTTPS webhook (Resend suggests ngrok locally). Unknown: size limit, retention, delete API, webhook signature method, SPF/DKIM results. Senior steps as above.
- **Forward-to-check, other inbound services (senior steps as above)**
  - Cloudflare Email Routing + Email Workers (1.5-2 d): the domain must be on Cloudflare DNS (adds MX, SPF, DKIM records); the Worker `email()` handler gets `raw` (parse with postal-mime), `headers`, `rawSize`, envelope from/to, `forward()`, `reply()`, `setReject()`; 25 MiB inbound; `reply()` once per event, to the sender only, from the receiving domain, and only if the incoming mail passes DMARC; routing is free on Free and Paid plans, Workers Free CPU limits can fail a handler (`EXCEEDED_CPU`); the Worker is the public endpoint but must call Scam Shield over HTTPS.
  - Amazon SES receiving (2-3 d): receipt rules on a verified domain, MX `inbound-smtp.<region>.amazonaws.com` (us-east-1, eu-west-1, eu-west-3 Paris, eu-central-1); actions S3 (40 MB max), SNS (150 KB, full copy), Lambda (no body), bounce, stop; SES writes `Authentication-Results` and `X-SES-Spam-Verdict`; $0.10 per 1,000 emails plus $0.09 per 1,000 incoming 256 KB chunks; no POP/IMAP.
  - Postmark Inbound: `yourhash@inbound.postmarkapp.com` with plus-addressing (`MailboxHash`) or an inbound domain; full JSON (`Headers[]`, `TextBody`, `HtmlBody`, `StrippedTextReply`, base64 attachments, SpamAssassin headers); 10 retries over ~10 h; inbound only on Pro and Platform (Basic $15/month; the free developer plan is 100 emails/month without inbound).
  - SendGrid Inbound Parse: MX `mx.sendgrid.net` priority 10 on a dedicated hostname; multipart POST with `headers, text, html, envelope, from, to, subject, sender_ip, attachments, attachment-info, dkim, SPF`, optional raw MIME, 30 MB total; the free plan was discontinued in 2025, 60-day trial at 100/day then Essentials $19.95/month (unverified).
  - Mailgun Routes: filter + `forward()` to an address or HTTP endpoint, `store()` keeps the message up to 3 days, parsed or raw MIME, retries over ~8 h; free 100 emails/day, 1 inbound route, 1-day logs; Basic $15/month (5 routes), Foundation $35/month (full inbound). Parsed field names not quoted.
  - On an inline forward every service checks SPF against the forwarder's MAIL FROM and the DKIM signatures present, so the pass belongs to the senior's provider, not to the scammer.
- **IMAP connector (3-4 d; +1 d for Outlook.com XOAUTH2)**; hosts on port 993 SSL/TLS, login = full address unless noted
  - Orange (orange.fr, wanadoo.fr): `imap.orange.fr`; password = "mot de passe dédié" for POP/IMAP/SMTP, created in Espace client > Connexion et Sécurité (espace-client.orange.fr/compte/securite#logiciels); Orange's own page both recommends it and lists it as a prerequisite; a Selectra page says the regular password no longer works (unverified); community threads (Aug 2026) report the 23-character dedicated password being refused (unverified). POP/IMAP toggle: webmail > roue crantée > tous les paramètres > Sécurité > Protocoles POP ou IMAP; "active by default" (2026 page) vs "off on new mailboxes" (2024 page). Probe: `AUTH=PLAIN AUTH=LOGIN`, Dovecot, no XOAUTH2, IDLE not listed pre-login (the banner says post-login has more; Dovecot normally has IDLE (unverified)).
  - SFR (sfr.fr, neuf.fr, club-internet.fr): `imap.sfr.fr`, `smtp.sfr.fr:465`, mailbox password (two secondary sources, unverified; assistance.sfr.fr could not be fetched); probe `IMAP4rev1 UIDPLUS AUTH=PLAIN`, no IDLE pre-login; numericable.fr/noos.fr use `imap.numericable.fr` (unverified).
  - Free: `imap.free.fr` on 993, else 143; full address required; probe `IMAP4REV1 X-NETSCAPE LOGIN-REFERRALS AUTH=PLAIN`, no IDLE pre-login; a 2022 third-party page says a "Fonctions POP3 / IMAP" option must be ticked (unverified).
  - Bouygues (bbox.fr): `imap.bbox.fr`, `smtp.bbox.fr:465`; probe `IMAP4rev1 ID LITERAL+ AUTH=LOGIN AUTH=PLAIN`, no IDLE pre-login; 1 GB mailbox (5 GB on Pro), 30 MB per email.
  - La Poste: `imap.laposte.net`, `smtp.laposte.net:587`, the webmail password; plain protocols cut 4 July 2023, TLS 1.2 minimum; probe `IMAP4rev1 UIDPLUS AUTH=PLAIN` (identical to SFR), no IDLE pre-login; POP/IMAP cut for all users for weeks in April-May 2022, restored 11 May 2022 (unverified).
  - iCloud: `imap.mail.me.com`, user = part before @ or the full address, app-specific password only (two-factor required; account.apple.com > Sign-In and Security > App-Specific Passwords > Generate; max 25 active; all revoked when the main password changes); no POP; probe `AUTH=ATOKEN AUTH=PLAIN AUTH=ATOKEN2 AUTH=XOAUTH2 XAPPLEPUSHSERVICE`, IDLE not listed pre-login; XOAUTH2 advertised but no third-party OAuth program found.
  - Yahoo/AOL: `imap.mail.yahoo.com` (`imap.aol.com` has the identical banner); app password from login.yahoo.com/account/security > External connections > Create app password; no 2-step prerequisite stated; stays active after a main-password change; eligibility automatic ("Customer care can't override"); probe `AUTH=PLAIN AUTH=XOAUTH2 AUTH=OAUTHBEARER`, `IDLE`, `MOVE`, `UIDPLUS`, `APPENDLIMIT=41697280`.
  - Outlook.com/Hotmail/Live: `outlook.office365.com`, `smtp-mail.outlook.com:587` STARTTLS; probe `AUTH=XOAUTH2 LOGINDISABLED SASL-IR UIDPLUS MOVE ID UNSELECT CHILDREN IDLE NAMESPACE LITERAL+`; Basic Auth gone since September 16, 2024; IMAP off by default (Settings > Mail > Forwarding and IMAP); flagged sign-ins need "This was me" at account.live.com/activity; XOAUTH2 scope `https://outlook.office.com/IMAP.AccessAsUser.All` + `offline_access`, SASL `base64("user=" + user + "^Aauth=Bearer " + token + "^A^A")`; connection cap not found.
  - Gmail: `imap.gmail.com`; probe `IDLE NAMESPACE QUOTA ID XLIST CHILDREN X-GM-EXT-1 AUTH=XOAUTH2 AUTH=PLAIN AUTH=PLAIN-CLIENTTOKEN AUTH=OAUTHBEARER`; XOAUTH2 scope `https://mail.google.com/` is Restricted and approval demands "full utilization" (Google says migrate to the API); app passwords need 2-Step Verification (myaccount.google.com/apppasswords), die on a password change, unavailable with security-keys-only 2SV or Advanced Protection; IMAP always on since January 2025; 15 clients per account; labels via `STORE 1 +X-GM-LABELS (foo)` and as folders; Workspace accounts lost password sign-in on May 1, 2025 (unverified wording). Do not build.
  - Library: imapflow 2.9.1 (2026-10-22, MIT, Node >= 20): one connection per instance, no reconnect (`InstanceReused` on a second `connect()`); CONDSTORE, QRESYNC, IDLE, COMPRESS handled automatically; Gmail `X-GM-EXT-1`; `auth.pass` or `auth.accessToken` (sends `AUTHENTICATE` XOAUTH2), `loginMethod`, `maxIdleTime` (restarts IDLE), `missingIdleCommand: 'NOOP' | 'SELECT' | 'STATUS'` polls every `maxIdleTime` on servers without IDLE, `socketTimeout`, `idle()`, `messageFlagsAdd(range, flags[])`, `messageMove(range, dest)`, `mailboxCreate`, `idlingAtClose`. mailparser 3.12.4 (Node >= 20, MIT, already in `package.json`; maintenance mode, security fixes only, PostalMime suggested for new projects; streams 100 MB+ messages).
  - Design: `POST /api/mailbox/connect {email, password|accessToken, provider?}` with a domain preset table (host, port, `missingIdleCommand`, walkthrough text) and a test login before saving; credentials in the existing AES-256-GCM token store (Outlook.com keeps a refresh token and mints access tokens); one `MailboxWorker` per user: new `ImapFlow` per attempt, `getMailboxLock('INBOX')`, `idle()`, exponential backoff 1 s to 15 min on `close`, `maxIdleTime` ~25 min (under the common 29-minute server cut), `missingIdleCommand: 'NOOP'` at 120 s for French ISPs; backfill the last 50 UIDs with `source` through `simpleParser` into the `normalizeMessage` shape (`src/google/gmail.js`) and `src/sync/checker.js`; incremental on `exists` above the stored `uidNext`, rescan on `uidValidity` change; `Sent` headers (To/Cc) for life context; never `\Deleted`, `expunge` or SMTP.
  - Effort split: presets + route + encryption 0.5 d; worker with reconnect/IDLE/polling + backfill + incremental 1.5 d; write-back + folder creation + tests on a fake server (Dovecot container or in-process) 1 d; senior walkthrough UI with per-provider screenshots 0.5-1 d; Outlook.com XOAUTH2 (Entra registration, consent, refresh) +1 d.
  - Risks: one TLS socket and one ImapFlow instance per user (1,000 users = 1,000 sockets, tens of MB per hundred connections (inference)); lockouts on a new server IP (Outlook.com "This was me", Orange refusals, La Poste 2022); Google and Apple passwords die on any password change, which silently stops protection unless the worker raises the existing "Please reconnect" banner; mailbox passwords at rest expose full mailboxes on a breach; 120 s re-logins at ISPs may trip limits (unquantified).
  - Steps, French ISP: 1) open Scam Shield, "Protect my email"; 2) type address and password (Orange: a relative generates the dedicated password in the Espace client first); 3) done. iCloud: turn on two-factor, generate an app-specific password, paste it (8-10 steps across two sites, relative-assisted); Yahoo/AOL ~5 steps on one page; Outlook.com: enable IMAP in settings, then OAuth consent (4-5 steps). Fallback: forward-to-check.
- **Write-back over IMAP (what the senior sees)**
  - Visible everywhere: `\Flagged` (flag in iPhone and Apple Mail (unverified), follow-up flag in Outlook on an IMAP account (unverified), star in Thunderbird (unverified) and in Gmail, where `\Flagged` = Starred) and a move to a `Scam Shield/Check first` folder (FR "À vérifier"; a folder in every client, a label on Gmail; the Orange webmail shows IMAP folders (unverified)). Mirror the two Gmail labels: `messageFlagsAdd(uid, ['\\Flagged', '$ScamShield'])` for Scam, `messageMove(uid, 'Scam Shield/Check first')` for Check first, folder created once. Moving a scam out of the inbox is the only write-back that changes an ISP webmail without client support.
  - Keywords: a server listing `\*` in PERMANENTFLAGS stores any atom (RFC 9051); Thunderbird renders `$label1..$label5` (Important red, Work, Personal, To Do, Later) and custom keywords once the user defines a tag with that key; Apple Mail colors are `$MailFlagBit0/1/2`, a private encoding that collides with the user's own flags (unverified); Outlook on an IMAP account keeps categories local and ignores keywords (unverified); Gmail stores keywords (case-sensitive on removal) but shows labels only, so use `X-GM-LABELS`; Orange webmail rendering unknown. Set keywords (cheap, reversible, machine-readable), never promise them.
  - Subject rewrite or an injected banner: impossible without re-appending the message (new Message-ID, broken threading).
- **Microsoft Graph for Outlook.com (2-3 d)**
  - Registration: an Azure account with an active subscription plus a tenant; account type "Personal accounts only" or "Any Entra ID tenant + personal Microsoft accounts"; publisher verification needs a Microsoft AI Cloud Partner Program account (free, blue badge; impossible for apps registered with a personal Microsoft account); without it the consent screen says "Unverified". Risk-based step-up consent (AADSTS90094) is a tenant policy for work accounts, so personal accounts should not hit it (inference, untested).
  - Read: `Mail.Read` / `Mail.ReadWrite` delegated for personal accounts, no admin consent; on loopback poll `/me/mailFolders('inbox')/messages/delta` every 120 s; change notifications on `/me/messages` or `/me/mailFolders('inbox')/messages` need a public HTTPS `notificationUrl` (validation handshake), last at most 10,080 minutes (1,440 with resource data), average latency under 1 minute, maximum 3 minutes, 1,000 active subscriptions per mailbox, lifecycle notifications, `$filter=isRead eq false` allowed, least privilege `Mail.ReadBasic`/`Mail.Read`; the `user` resource is unsupported for personal accounts, `message` carries no such caveat.
  - Write-back: `PATCH /me/messages/{id}` with `Mail.ReadWrite` sets `categories`, `flag`, `importance`, `inferenceClassification` (Focused/Other), `isRead`; body and subject only while `isDraft`; categories come from the per-user master list (`displayName` + `color`, 25 presets, `preset0` red, `preset1` orange, rendering client-dependent) and show as a colored named label in every Outlook client; `move` for Check first.
  - Limits: 10,000 requests per 10 minutes and 4 concurrent requests per app ID + mailbox; 150 MB upload per 5 minutes; JSON batches run 4 requests in parallel.
  - Steps: 1) tap "Protect my email"; 2) Microsoft sign-in; 3) accept the consent marked "Unverified". Fallback: forward-to-check.
  - A "Check this" button inside Outlook is an Outlook add-in (manifest + JS/HTML, runs on Outlook.com consumer accounts in web, Windows, Mac, iOS and Android, from Marketplace or sideloaded, needs a network connection and a public HTTPS origin, never activates on a `.eml` attachment): the Outlook twin of feasibility #4, not a sync path; not estimated.

## Corrections to feasibility.md
- #2: Outside Gmail, IDLE is advertised only by Yahoo/AOL and Outlook.com; the French ISPs and iCloud show none pre-login, so promise "about two minutes" (120 s poll) there; under one minute only with Graph webhooks (public HTTPS).
- #3: IMAP is no way around verification: the IMAP scope `https://mail.google.com/` is Restricted too and its approval demands "full utilization"; app passwords need 2-Step Verification and die on a password change. Keep `gmail.modify`.
- #4: The Outlook twin exists: Outlook add-ins run on Outlook.com consumer accounts, sideload for a demo, need a public HTTPS origin, and never activate on a `.eml` attachment, so a button cannot combine with forward-to-check.
- #15: The fastest universal entry point is forward-to-check: 0.5 day on a polled `check@` Gmail, 1-1.5 days on Resend Receiving (free, 100/day, no DNS); an inline forward loses the original SPF/DKIM, so the verdict must say so.
- #19: Forwarded copies sit at Resend (30-day logs on Free, delete API unknown), which breaks "bodies never stored" unless deleted; an IMAP connector holds mailbox passwords at rest, a larger liability than OAuth tokens.
- #25: Resend, Cloudflare, SES and Graph webhooks need the public URL; the polled `check@` Gmail, the IMAP connector and Graph delta polling need none, so forward-to-check and IMAP can ship on loopback.

## Gaps
- Post-login IDLE for Orange, SFR, Free, Bouygues, La Poste and iCloud: only pre-login banners were read; needs a real login on day 1.
- Orange: whether the regular password still works over IMAP (Orange's pages contradict each other, Selectra says no) and the reported refusals of the dedicated password; test on a real Orange account from the server IP.
- SFR: no official page could be fetched; settings come from two secondary sources that agree.
- Connection and login-rate limits for Orange, SFR, Free, Bouygues, La Poste, Yahoo and Outlook.com: not published; the cost of 120 s re-logins is unquantified.
- Whether a personal Microsoft account can consent to an unverified "Personal accounts only" app asking `Mail.ReadWrite` or `IMAP.AccessAsUser.All`: 30-minute test with a throwaway outlook.com account.
- Graph change notifications for Outlook.com consumer mailboxes in practice: untested; add-in sideloading on Outlook.com by a non-admin: page not read.
- Rendering of `\Flagged` and keywords in iPhone Mail, Apple Mail and the Orange webmail: 10-minute test on real accounts; Gmail web's treatment of IMAP keywords: indirect evidence only.
- imapflow event names (`exists`, `flags`, `expunge`) and the `missingIdleCommand` default: not quoted (API reference returned 404; only the typings were read).
- Resend: size limit, retention of received mail, delete API, webhook signature method, and whether SPF/DKIM results come through the Received-email API: unknown.
- Mailgun's parsed POST field names: not quoted.
- Forward as attachment on the Orange webmail, the Orange/SFR mobile apps, Gmail mobile, iPhone Mail and new Outlook: no official source.
- All day estimates are for one engineer who knows the repo and were not validated on a prototype; the IMAP demo depends on an untested Orange/SFR login from a server IP.
