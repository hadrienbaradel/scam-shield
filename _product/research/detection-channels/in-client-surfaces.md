# In-client verdict surfaces: where the senior sees the verdict and taps inside the mail client

Answers, dated 2026-10-28: for each mail client a senior already uses, where Scam Shield's verdict can show in place, where a "Check this / Ask" button can live, what each surface needs, how long it takes and whether it fits before Nov 4. Condensed from the detection-channels research notes; "(unverified)" marks claims not checked at an official source.

## Decision

For the Nov 4 video: Gmail. Keep the built labels as the passive marker and add an Apps Script Gmail add-on card (1.5-2 days), filmed on a phone and on the web; add the Chrome InboxSDK notice bar (1-2 days) only if the storyboard keeps a desktop scene. The add-on is the only tappable in-place surface on Gmail web, Android and iOS that needs no store and no new Restricted scope (at most the Sensitive `gmail.addons.current.message.metadata`; the sync's `gmail.modify` token does the labelling). For real seniors after Nov 4: IMAP flags and folders first (1-2 days; one channel covers Orange, Free, SFR, La Poste, Yahoo/AOL, iCloud and Apple Mail on iPhone and Mac with nothing installed on the device), then the Outlook task pane, then MailKit. No mail client lets a third party interrupt the senior, so the Scam Shield app stays the place for the interruption, the spoken explanation and the trusted-person loop; in-client surfaces mark the message and hand off.

## Build sheet

- **Gmail add-on (Apps Script, Google Workspace add-on)**
  - Scopes: `gmail.addons.current.message.metadata` (Sensitive: temporary access to the open message's subject and recipients, needs the event access token) or `gmail.addons.current.message.readonly` (Sensitive: metadata and content, plus the other messages in the thread); `gmail.addons.current.message.action` and `gmail.addons.current.action.compose` are Non-sensitive (content only after the senior taps); `gmail.labels` (Non-sensitive) creates and lists labels, but applying one needs `messages.modify` with `gmail.modify`, `gmail.modify.restricted` or `https://mail.google.com/` (Restricted; up to 100 labels per update), so label and move go through the server's existing token. UrlFetch needs `script.external_request` (class unverified). Restricted scopes may be used freely in a non-public add-on; Sensitive scopes need OAuth verification before a public listing, no CASA.
  - Trigger: the only contextual trigger is unconditional; it fires when the senior opens a message while the add-on is open, starts the add-on on a message, or switches message; the function must return an array of Cards; the event carries `e.gmail.messageId`, `e.gmail.accessToken` (`GmailApp.setCurrentMessageAccessToken`) and `commonEventObject.platform` (WEB, IOS, ANDROID); a homepage card shows without message context. Whether `messageId` arrives with no Gmail add-on scope is not stated (unverified).
  - Widgets: card header (title, subtitle, image), sections, TextParagraph with `<b> <i> <u> <s> <font color> <a href> <time> <br>`, DecoratedText (plain top and bottom labels, icon or picture, button or switch), Image (public URL), Grid, text and image buttons with a fill colour, fixed footer with primary and secondary buttons, selection and text inputs; actions: run a function, open a URL, navigate cards, notification, draft. No custom HTML, no polling, no auto-open, no notification; peek cards are web-only. Design: three verdict cards with red, orange and green DecoratedText icons and two buttons ("Ask my daughter", "Put it back" or "Open in Scam Shield"); "Checking..." plus a refresh button when the verdict is not stored yet.
  - Quotas (Apps Script, consumer account, page of 2026-09-03): URL Fetch 20,000/day (100,000 on Workspace), add-on runtime 30 s per execution, 30 simultaneous executions per user, triggers total runtime 90 min/day, email read/write 20,000/day, URL Fetch response 50 MB, URL length 2 KB. Latency: no official figure; a community thread timed a contextual card at about 6 s (unverified); actions past about 30 s show "could not perform this add-on action".
  - Install, demo: Apps Script editor > Deploy > Test deployments > Install > Done, then refresh Gmail; one Google account signed in (multi-login is unsupported for add-ons). Other testers need editor access on the script project and "the same domain as the script owner"; two @gmail.com accounts: unclear, test on day 1 (a 2023 community thread shows an editor's install hanging while the owner's worked (unverified)). The HTTP runtime (our Node server as backend: POST JSON event in, card JSON out, verify `authorizationEventObject.systemIdToken`) flags "iOS capabilities" as not yet supported, so build in Apps Script for the phone demo.
  - Install, public: a consumer account can only publish Public (Private and Unlisted need a Workspace account; the choice cannot be changed later); Marketplace review "several days" after OAuth verification (homepage on a verified domain proven in Search Console, privacy policy on the same domain, demo video of the OAuth flow, scope justification; the app must be in production first); an unverified app shows the warning screen and is capped at 100 new users; Testing mode: 100 test users, consent expires after 7 days. Weeks, not before Nov 4.
  - Senior, phone: 1) open the email; 2) scroll to the end of the message; 3) tap the Scam Shield icon; 4) read the card, tap "Ask my daughter". Web: 1) open the email; 2) click the Scam Shield icon in the right side panel. Fallback: labels plus the app.
- **Gmail labels (built, `src/google/gmail.js`)**
  - API: 102 predefined colours only (#fb4c2f and #ffad47 are in it, as are #ffffff, #000000, #cc3a21, #ac2b16, #fad165, #16a766); `backgroundColor` and `textColor` both required; colour only on user labels; 10,000 labels per mailbox (the help page says 5,000 labels and 100 custom colours); nesting with "/"; `labelListVisibility` labelShow / labelShowIfUnread / labelHide and `messageListVisibility` show / hide apply to the web interface; `messages.modify` touches one message, `threads.modify` all existing messages and new ones do not inherit; INBOX, SPAM, TRASH, UNREAD, STARRED, IMPORTANT and CATEGORY_* can be applied, SENT and DRAFT cannot. The repo creates both labels with labelShow / show, falls back to no colour on a 400 and refuses SPAM, TRASH, DRAFT and SENT.
  - Phones: label colours are editable on the web only (Android got label creation in February 2026); chip rendering in the phone conversation list and the nested path are undocumented (unverified); a message with INBOX removed sits under the label and "All mail", not in Spam; a reply returns the thread to the inbox, so the sync must label the new message again (seconds on push, about 2 minutes on poll). Stars and importance markers turned blue on the web in September 2026: do not star scams. Fallback: none needed; verify on a device (10 minutes).
- **Chrome extension on Gmail web (InboxSDK)**
  - Library: `@inboxsdk/core` on npm, MV3 build with no remote loading, MIT and Apache 2.0, maintained by Streak, free App ID at register.inboxsdk.com (seconds); current version unverified (npm page returned 403). Scaffold: `InboxSDK/hello-world` (`npm install`, `npm start`, load `dist` unpacked). gmail.js is injected into the page (not a content script), needs jQuery and relies on deprecated XHR calls "very likely to fail": avoid.
  - APIs: `ThreadView.addNoticeBar()` (bar below the subject, yellow by default, restylable), `ThreadView.addLabel()`, `ThreadView.addSidebarContentPanel({el, title, iconUrl})` (our HTML), `MessageView.addToolbarButton()` (hidden in the More menu, not for seniors), `MessageView.getBodyElement()`, `getSender()`, `getMessageIDAsync()`; `registerThreadRowViewHandler` plus `ThreadRowView.addLabel({title, iconUrl, foregroundColor, backgroundColor, maxWidth})` (temporary visual, default max width 90px). Auth: the content script posts the message id with a device token like the Android companion (the session cookie is same-site and the server checks Origin); the server returns the stored verdict; no Gmail scope.
  - Install, demo: chrome://extensions > Developer mode > Load unpacked. Public: Web Store review "within a few days, up to a few weeks", longer for new developers and broad host permissions (mail.google.com), contact support after three weeks; Unlisted and Private go through the same review; $5 registration (2020 Chromium blog figure, not on the current page); new publishers limited to two extensions; Edge takes the same code with minimal changes but its own listing. Senior: 1) open the email in Chrome; 2) the red bar under the subject shows the verdict and the buttons; 3) tap "Ask my daughter". Fallback: the add-on side panel.
- **Outlook add-in (Office.js)**
  - Coverage: Outlook on the web (outlook.live.com, outlook.office.com), new and classic Windows, Mac, iOS, Android; Outlook.com and Microsoft 365 mailboxes only; Gmail, Yahoo and IMAP accounts added to Outlook get nothing (Mac "IMAP CloudCache" excepted); no add-ins in Outlook on the web on a phone browser. Requirement sets: web and Windows Mailbox 1.1-1.16, Mac 1.1-1.14, Android and iOS 1.1-1.5 plus NestedAppAuth 1.1; mobile is Message Read only (`MobileMessageReadCommandSurface`), XML add-in-only manifest with `<MobileFormFactor>` (the unified JSON manifest is unsupported on mobile and Mac); unsupported on mobile: getCallbackTokenAsync, makeEwsRequestAsync, displayReplyForm, getRegexMatches, categories.
  - Reads: `item.subject`, `item.from`, `item.body.getAsync`, `item.itemId` (REST id on mobile, EWS id elsewhere, `convertToRestId`), `getAllInternetHeadersAsync` (Mailbox 1.8, read mode; mobile support conflicting (unverified)), `getAsFileAsync` (Base64 EML). Shows: a task pane (our HTML) after the tap; a `notificationMessages.replaceAsync` bar above the body (Mailbox 1.3; Error, Informational and Progress on all clients; up to 5 per message, 1 on mobile; key at most 32 characters; a 150-character text limit is from memory (unverified)); colour categories (Mailbox 1.8, `masterCategories.addAsync` then `item.categories.addAsync`, read/write item, desktop and web only); a pinned pane refreshed on `ItemChanged` only for Microsoft 365 subscribers on desktop and web, never Outlook.com or mobile (+0.5 day).
  - Limits: no message-read event (OnMessageReadWithCustomHeader is preview, classic Windows Version 2312+, Insider Beta; event-based add-ins launch only when admin-deployed, 300 s timeout, five at a time); moves and flags need Microsoft Graph with NAA (MSAL `createNestablePublicClientApplication`, an Entra app with a `brk-multihub://<domain>` redirect, authority "common"; callback and REST tokens are turned off; third-party EWS blocked from 2026-10-01 (unverified)): 1-2 days, defer; the integrated spam-report button (Mailbox 1.14, `event.completed({moveItemTo: JunkFolder})`, 5-minute limit, 1-2 days) is unavailable on mobile and for consumer accounts on web and new Windows.
  - Install, demo: `yo office` task pane, pane served from Fastify behind the tunnel (HTTPS reachable from the phone); https://aka.ms/olksideload > My add-ins > Custom Addins > Add a custom add-in > Add from File (Add from URL removed); the same account then has it on Mac and on the phones; classic Windows may take up to 24 h and needs the Reading Pane on Right or Bottom; the manifest hard-codes the host. Public: Partner Center with an Entra work account, legal business name and address, privacy policy and support URLs, HTTPS, touch-only operation, Outlook on the web support; review 3-5 working days plus a mobile design review and an Apple Developer ID for iOS; a restricted listing hides behind a flight code; the free Microsoft 365 E5 sandbox is limited to Visual Studio subscribers, partners and Premier customers (90 days, billing account required).
  - Senior, web or new Windows: 1) open the email; 2) tap Apps on the message action bar (or More apps on the ribbon); 3) tap Scam Shield; a helper can right-click > Pin to make it one tap. Phone: 1) open the email; 2) tap the three dots; 3) tap Scam Shield. Classic Windows: Home tab > Scam Shield (All Apps if hidden). Fallback: forward to the app.
- **Apple Mail on Mac (MailKit action handler)**
  - API (macOS 12+, documented through macOS 26/27): `MEExtension` with `MEExtensionCapabilities` = `MEMessageActionHandler`; `decideAction(for:completionHandler:)` runs for every new message before it is visible, first with headers only (`fromAddress`, `toAddresses`, `subject`, `headers`); return `invokeAgainWithBody` to get `rawData` (RFC 2822); decisions `action(_:)` or `actions([...])` from `markAsRead`, `markAsUnread`, `flag(...)`, `setBackgroundColor(...)`, `moveToJunk`, `moveToArchive`, `moveToTrash`; no custom mailbox, no text, no banner, no button; Mail shows an "extension acted" icon in the header; always call the completion handler; no time budget documented, and Mail holds the message until the decision. Inbox-bound messages only (developer forum, unverified). NSURLSession is allowed from extensions; the sandbox entitlement `com.apple.security.network.client` is assumed (unverified). The other extension types cannot carry a verdict: a content blocker returns static Safari-style JSON rules, a security handler only renders a signer label and a certificate view.
  - Setup: Xcode Mail Extension template, sample "Build Mail App Extensions" (macOS 12, Xcode 15.2), WWDC21 session 10168. On macOS 26 (one forum report, unverified): discovery moved to ExtensionFoundation, the host app must sit in /Applications, Info.plist needs both NSExtension and an XPCService block, the Mail > Settings > Extensions checkbox is unchecked by default and resets on each rebuild, `pluginkit -m -A -i <bundle id>` checks registration, the extension process spawns only when mail arrives. Public: $99/yr Apple Developer Program, Developer ID plus notarization or the Mac App Store; a Personal-Team-signed local build is unverified. Senior: 1) a relative installs the app in /Applications; 2) Mail > Settings > Extensions, tick Scam Shield; 3) nothing else. Fallback: an IMAP flag on the same account.
- **Apple Mail on iPhone**
  - MailKit is macOS-only; iOS Mail has no Share of a whole message (only of attachments); the Shortcuts Email trigger filters on Sender, Subject Contains, Account and Recipient and is not documented to hand over the message; .eml export is a drag-into-compose trick. The app shows server state only: a colour-codable flag icon beside the thread, a Flagged mailbox, custom mailboxes under the account; with iOS 18.2+ categories on, Promotions, Updates and Transactions cannot be flagged. Build nothing here; the IMAP channel is the surface.
- **IMAP flags and folders (server-side, one Node IMAP client)**
  - Servers, all port 993 with SSL: iCloud `imap.mail.me.com` with an app-specific password (two-factor required, up to 25 active, account.apple.com > Sign-In and Security); Yahoo and AOL `imap.mail.yahoo.com` with an app password (Account Security > External connections > Create app password, shown once); La Poste `imap.laposte.net` with the account password; Free `imap.free.fr` with the full address as login; Orange `imap.orange.fr`, full address (search snippet, unverified; users can switch IMAP off in the security settings (unverified)); SFR `imap.sfr.fr` (third-party, unverified; the official page blocks crawlers); Gmail over IMAP needs XOAUTH2 with the full `https://mail.google.com/` scope (Restricted, "must show full utilization"), so Gmail stays on the API.
  - Actions: set and clear `\Flagged` (iOS flag colours map to `$MailFlagBit0..2` keywords (unverified)), create and move into "Scam Shield/Check first" and "Scam Shield/Scam", mark read; never delete or send. No provider documents how foreign flags and folders render in its webmail or app: budget 0.5 day per provider to check by hand. The server holds the credential (encrypt it like the Gmail tokens). Senior: 1) a relative opens Scam Shield > Add a mailbox; 2) picks the provider; 3) enters the address and the password or app password once; 4) nothing else. Fallback: forward to a Scam Shield address.
- **ISP webmails and Yahoo (Orange, Free, SFR, La Poste, Yahoo, AOL)**
  - No add-on or extension API; Free's webmail host is zimbra.free.fr and Zimbra zimlets are deployed by the administrator per Class of Service (search snippet, unverified); Yahoo's only developer API dates from 2007. Market: no recent French survey by provider; a 2019 ranking puts Gmail and Outlook.com first, Orange third, Yahoo fourth, SFR fifth; Médiamétrie January 2019 reach Gmail 46.6%, Outlook 23.4%, Orange 22.2%, SFR 10.3%, Yahoo 8.1% (unverified); US over-65 (Morning Consult 2017) Yahoo 31%, Gmail 24%, AOL 16% (unverified). Both argue for IMAP as the second channel after Gmail.
