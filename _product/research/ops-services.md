# Ops services: error tracking, monitoring, hosting, shared database, deploys

Vlad's ask of 2026-10-29: errors in Rollbar, a deployment outside our laptops, one Postgres both developers share over Tailscale, deploy often and check Rollbar after each deploy, free production monitoring. Checked on the vendors' own pages on 2026-10-29, for a six-day horizon (due Nov 4) and about 5-10 € a month; prices without VAT.

## A. Rollbar (error tracking)

- **Free plan:** $0, 5,000 occurrences and 1,000 session replays a month, 30-day retention, unlimited users and projects ("Rollbar never charges per seat"), deploy and version tracking included. At the cap processing stops until the next cycle (events dropped); next step Essentials from $9 for 10,000. Which alert channels Free gets (email, Slack) is not stated (unverified).
- **Rate limits:** no published number; over a limit the API answers 429 and the item is neither stored nor billed; the SDK caps itself at `itemsPerMinute: 60`. One job failing every 2 minutes (the Gmail poll) is 720 items a day: the month's 5,000 in about 7 days. Report a job on its ok-to-failing transition, not on every tick.
- **SDK:** `rollbar` 4.2.0 ships an ESM entry for Node (`import Rollbar from "rollbar"`). No Fastify middleware (Express `errorHandler()`, Koa and Hapi examples only), so: one module, a call in the existing `app.setErrorHandler` of `src/server.js` (status >= 500 only), one in `note()` of `src/jobs/scheduler.js` (job errors are caught there and never reach the handler; the poll masks addresses before calling it, and its `ADDRESS` regex can serve the Rollbar `transform`).
- **Options:** `accessToken` (a post_server_item token); `environment` defaults to `NODE_ENV` (the prod compose gives `production`, laptops `development`); `codeVersion` = the git sha baked into the image; `captureUncaught`, `captureUnhandledRejections`, and `exitOnUncaughtException: true`, without which Rollbar's listener keeps a broken process alive instead of letting `restart: unless-stopped` restart it; `captureIp: false`. `captureEmail`, `captureUsername`, `autoInstrument` and `locals` are off by default and stay off (telemetry would ship console lines).
- **Personal data:** `rollbar.error(err, request)` with Fastify's request sends every header (authorization and cookie are scrubbed by default), `req.body` (a pasted message, a phone number), the full URL with its query (`/auth/google/callback?code=...`: `code` and `state` are not on the default scrub list) and `person.id` from `request.user`, which our `onRequest` hook sets. Fix: `addRequestData: (data, req) => { data.request = { method: req.method, url: req.routeOptions?.url }; }`; with that hook set, Rollbar skips its own request, IP and person extraction. Second net: `scrubFields` (body, text, snippet, subject, from, to, email, phone, mobile, code, state, refresh_token, id_token; added to the defaults) and a `transform` that masks addresses and phone numbers in error messages.
- **Deploy marker:** `POST https://api.rollbar.com/api/1/deploy` with header `X-Rollbar-Access-Token` (post_server_item), JSON `environment`, `revision` (git sha), optional `local_username`, `comment`, `status` (started, succeeded, failed, timed_out); also packaged as `rollbar/github-deploy-action@2.1.2`. The after-deploy check can be automatic: `GET https://api.rollbar.com/api/1/items/?environment=production&status=active&level=error&level=critical` with a read token, failing when an item's `last_occurrence_timestamp` is later than the deploy.
- **Sentry instead:** the free Developer plan is 1 user, 5k errors, email alerts only, 30-day lookback (plus 1 cron and 1 uptime monitor). `@sentry/node` has `fastifyIntegration` (route and hook errors captured without a handler, loaded with `node --import ./instrument.mjs`, Node 22.12+ while we allow 22.9) and sends IP, user and bodies unless `dataCollection` turns them off. One seat for two developers rules it out.

Recommendation: Rollbar Free, one project; `ROLLBAR_ACCESS_TOKEN` through `make secrets-set`, a deploy token and a read token as GitHub Actions secrets; route-only `addRequestData`, never the raw request.

## C. Tailscale and one shared Postgres

- **Personal plan (free):** up to 6 users, unlimited user devices, 50 tagged resources, 3 ACL groups, 1,000 minutes a month of ephemeral nodes (limits announced, not enforced yet), Tailscale SSH on all plans; "only suitable for non-commercial use"; a tailnet on a public domain such as gmail.com lands on Personal automatically.
- **Two developers:** invite Hadrien into Vlad's tailnet ("Invite external users", any email, all plans; he becomes one of the 6), so one policy covers both. Sharing the server node with Hadrien's own tailnet also works on all plans, but the shared node cannot open connections back, tags and groups do not carry over and he must use the full MagicDNS name: the invite is simpler.
- **Tailscale SSH:** `tailscale set --ssh` on the host; tailscaled answers port 22 on the tailnet address only; access lives in the policy's `ssh` rules (`accept`, or `check` with re-authentication, every 12 h by default). The public sshd can then be closed at the cloud firewall.
- **Postgres on the tailnet only:** publish `"<host 100.x IP>:5432:5432"` in the prod compose, never a bare `5432:5432` (Docker-published ports bypass ufw). Docker can start before tailscaled holds the 100.x address ("cannot assign requested address" after a reboot): set `net.ipv4.ip_nonlocal_bind=1` (ordering docker after tailscaled alone may not wait for the address, unverified). Simpler and race-free: publish `127.0.0.1:5432:5432` and run `tailscale serve --bg --tcp=5432 tcp://127.0.0.1:5432` (tailnet only, access rules apply; Serve asks for HTTPS certificates to be enabled in the tailnet).
- **pg_hba.conf:** the official image appends `host all all all scram-sha-256` at first start; replace it with `host all all 100.64.0.0/10 scram-sha-256` plus the compose subnet for the app (Docker's DNAT keeps the 100.x source address, unverified; through `tailscale serve` connections arrive from Docker's gateway, so the tailnet policy is the gate). One role per developer, not the app's owner role.
- **Policy sketch:** `"tagOwners": {"tag:prod": ["autogroup:admin"], "tag:ci": ["autogroup:admin"]}`; grants `{"src": ["autogroup:member"], "dst": ["tag:prod"], "ip": ["tcp:5432", "tcp:22"]}` and `{"src": ["tag:ci"], "dst": ["tag:prod"], "ip": ["tcp:22"]}`; ssh `{"action": "accept", "src": ["autogroup:member", "tag:ci"], "dst": ["tag:prod"], "users": ["deploy"]}`. Grants deny by default, so this replaces the allow-all starter policy.
- **Latency measured today** (WonderNetwork, round trip): Boston to Washington/Ashburn 12 ms, London 78, Paris 78, Frankfurt 85, Nuremberg (next to Falkenstein) 97; Paris to London 8, Frankfurt 15, Washington 78. No place is near both of us: one developer pays 80-100 ms whatever we pick, and London or Paris does not help Boston.
- **What that does to the app:** queries run one after another, so a laptop app on the remote database adds 5-10 round trips per page: 0.4-1.0 s for whoever is across the ocean, 0.05-0.15 s for the other, far more on a Gmail backfill (hundreds of queries). The deployed app sits next to its database (under a millisecond); a browser pays one round trip per request, unnoticeable.

Recommendation: each laptop keeps its own Postgres for daily work; the shared one is the host's, holds the demo data and is used on purpose: psql or TablePlus over the tailnet, or the laptop app with `DATABASE_URL` pointed at it and `WORKER=0` (production alone runs the jobs; per-user syncs already take an advisory lock), only from main (the app migrates at start), never as `TEST_DATABASE_URL` (the suite truncates). The host's location then follows the account (D); on a tie, US East: Hadrien, the US judges, and Meta's API (EU access still open in `research/meta-ai-stack.md`).

## E. Public HTTPS on a VPS

- **Cloudflare Tunnel:** "Available on all plans", "No open inbound ports. No public IPs."; a `cloudflared` service in the prod compose running `cloudflared tunnel run --token <TUNNEL_TOKEN>` (or `TUNNEL_TOKEN` in its environment, `TUNNEL_TOKEN_FILE` since 2025.4.0), with the published route demo.heyprudence.com to http://app:3000 on the compose network; the dashboard creates the DNS record (unverified). The tunnel lives in the Cloudflare account that holds the zone (Hadrien's): he creates it, or adds Vlad to the account. A request still waiting after 125 s ends in a 524 (only Enterprise can raise it); a Muse check takes about 5 s.
- **Caddy:** automatic Let's Encrypt once the A record points at the host, ports 80 and 443 are open and its data directory persists; renews by itself; the Caddyfile is `demo.heyprudence.com { reverse_proxy app:3000 }`. Behind Cloudflare's proxy (orange cloud) the SSL mode must be Full (strict) (unverified); a grey-cloud record is simplest.
- **Google OAuth:** redirect URIs must be HTTPS (localhost exempt), cannot be raw IP addresses, and must match exactly (scheme, case, trailing slash): register `https://demo.heyprudence.com/auth/google/callback` (the app builds it from `BASE_URL`) next to the localhost one.
- **Either way:** `src/server.js` sets `trustProxy: false`, so behind a proxy `request.ip` is the proxy's address and every signed-out visitor shares one rate-limit bucket; trust the proxy's address (the compose network) when deployed.

Recommendation: Cloudflare Tunnel: no ports, no certificates, the domain is already on Cloudflare, and with Tailscale SSH the host keeps no inbound TCP port open. Caddy only if Hadrien's Cloudflare account cannot be used.

## F. Deploy on every push to main

- **Shape 1, SSH and build on the host** (`git pull && docker compose up -d --build --wait`): build memory on a 1-2 GB box, a rollback is a rebuild; secrets: host, user, a private deploy key and the host-key `fingerprint` for `appleboy/ssh-action@v1` (`ssh-keygen -l -f /etc/ssh/ssh_host_ed25519_key.pub | cut -d ' ' -f2`), plus port 22 open to GitHub's runners and a repo read key on the host.
- **Shape 2, build in CI, push to GHCR, the host pulls:** the image that passed CI is the one that runs; tag it with the sha and roll back by starting the previous tag (the compose file already reads `APP_IMAGE`). `GITHUB_TOKEN` pushes packages tied to the repo; a private package needs a classic PAT with `read:packages` on the host (fine-grained tokens are not supported); public images pull anonymously.
- **Shape 3, Watchtower polling GHCR:** the repository was archived on 2025-12-17, "no longer maintained", and it deploys outside CI, so no marker at the right moment. No.
- **Reaching the host without public SSH:** `tailscale/github-action@v4` joins the runner as an ephemeral `tag:ci` node (an OAuth client id and secret, or workload identity federation with `id-token: write`), then `tailscale ssh deploy@<host>`, with no SSH key or known_hosts secret (unverified for how `tailscale ssh` handles host keys on a fresh runner).
- **Rollbar marker step** (`if: always()`): `curl -fsS -X POST https://api.rollbar.com/api/1/deploy -H "X-Rollbar-Access-Token: $ROLLBAR_DEPLOY_TOKEN" -H "Content-Type: application/json" -d "{\"environment\":\"production\",\"revision\":\"$GITHUB_SHA\",\"local_username\":\"$GITHUB_ACTOR\",\"status\":\"$STATUS\"}"` with `STATUS` = `succeeded`, or `failed` when an earlier step failed.
- **GitHub constraints:** the repo is private today (404 without login); on GitHub Free that means no Environments (no required reviewers) and $12 of included usage, about 2,000 Linux minutes a month at $0.006, after which jobs are blocked without a card; public repos run standard runners free. Migrations run at app start, so rolling the image back does not roll the schema back: keep migrations additive until Nov 4.

Recommendation: shape 2 over Tailscale, as a `deploy` job in `.github/workflows/ci.yml` with `needs: node`, `if: github.ref == 'refs/heads/main' && vars.DEPLOY_ENABLED != 'false'` and `concurrency: deploy` (never cancelled): build and push `ghcr.io/hadrienbaradel/scam-shield:<sha>`, join the tailnet, `APP_IMAGE=<that tag> docker compose pull app && docker compose up -d --no-build --wait`, poll `/api/health` until it reports the new sha (else start the previous sha again), post the Rollbar marker, and five minutes later fail the job if Rollbar shows an active error newer than the deploy. Set `DEPLOY_ENABLED=false` while the video is recorded.
